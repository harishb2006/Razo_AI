# Deploying Razo_AI

Two services, both on Render's free tier, both defined in [`render.yaml`](../render.yaml).
Total cost ₹0 and no card required at any step.

| Service | What it is | Free-tier catch |
|---|---|---|
| `razo-ai-api` | FastAPI backend, from `backend/Dockerfile` | Sleeps after 15 min idle; first request then takes ~40s |
| `razo-ai-web` | React app, static build of `client/` | None |

> **The cold start is the one thing that can spoil a live demo.** Open the
> deployed URL five minutes before you present so the service is awake. There
> is a warm-up step in the demo runbook for exactly this reason.

---

## Before you start

You need four things. All are free, none need a payment method.

1. **MongoDB Atlas M0 cluster** — <https://cloud.mongodb.com>
   Create a free M0 cluster, add a database user, and under *Network Access*
   allow `0.0.0.0/0` (Render's free tier has no fixed egress IP, so an IP
   allowlist won't work). Copy the `mongodb+srv://...` connection string.
2. **Razorpay test-mode keys** — Dashboard → Settings → API Keys, in **Test Mode**.
   You want `rzp_test_...` and its secret. Never the live pair.
3. **A Gemini API key** — <https://aistudio.google.com/apikey> (optional).
4. **A Groq API key** — <https://console.groq.com/keys> (optional).

Both LLM keys are genuinely optional: the provider chain falls back to a
built-in offline `echo` provider, so the demo answers even with no keys at all.

---

## Step 1 — Seed the catalog

Render's free tier gives you no shell, so seed Atlas from your own machine.

```bash
cd backend
MONGODB_URI='mongodb+srv://USER:PASS@cluster.mongodb.net/' \
MONGODB_DB=razo_ai \
OFFLINE_MODE=False \
./venv/bin/python -m scripts.seed_catalog
```

You should see 64 products written. Do this once, before the first deploy.

---

## Step 2 — Create the blueprint

In the Render dashboard: **New → Blueprint**, pick the `Razo_AI` repo, and
Render reads `render.yaml` and offers both services.

It will prompt for every value marked `sync: false`:

| Variable | Service | Value |
|---|---|---|
| `MONGODB_URI` | api | Your Atlas connection string |
| `MONGODB_AUDIT_URI` | api | Insert-only Atlas user, or leave blank to reuse the above |
| `CORS_ORIGINS` | api | Leave blank for now — Step 3 |
| `GEMINI_API_KEY` | api | Your key, or blank |
| `GROQ_API_KEY` | api | Your key, or blank |
| `RAZORPAY_KEY_ID` | api | `rzp_test_...` |
| `RAZORPAY_KEY_SECRET` | api | Test secret |
| `RAZORPAY_WEBHOOK_SECRET` | api | Step 4 — blank for now |
| `VITE_API_BASE_URL` | web | Leave blank for now — Step 3 |
| `VITE_API_KEY` | web | Step 3 |

`API_KEY` and `VERDICT_SIGNING_KEY` are generated by Render — you don't type those.

Deploy the **API first** so you know its URL before the web build runs.

---

## Step 3 — Wire the two together

This is the step everyone forgets, and it produces a blank page with a CORS
error in the console.

Once the API is live at `https://razo-ai-api.onrender.com`:

1. **Copy the generated API key.** API service → Environment → `API_KEY` → reveal.
2. **On `razo-ai-web`**, set:
   - `VITE_API_BASE_URL` = `https://razo-ai-api.onrender.com/api/v1`
   - `VITE_API_KEY` = the value you just copied
3. **On `razo-ai-api`**, set:
   - `CORS_ORIGINS` = `["https://razo-ai-web.onrender.com"]`
     (a JSON array, with the quotes and brackets, and **no trailing slash**)
4. Redeploy **both**. `VITE_*` variables are baked in at build time, so the
   web service must rebuild to pick them up — restarting is not enough.

---

## Step 4 — Razorpay webhook

Razorpay Dashboard → Settings → Webhooks → Add New Webhook.

- **URL**: `https://razo-ai-api.onrender.com/api/v1/webhooks/razorpay`
- **Secret**: generate one (`openssl rand -hex 32`), then set it as
  `RAZORPAY_WEBHOOK_SECRET` on the API service and redeploy.
- **Events**: `payment_link.paid`, `payment.captured`, `payment.failed`

Signatures are verified on every webhook; an unsigned or mis-signed call is
rejected. That behaviour is covered by `backend/tests/test_webhook_signature.py`.

---

## Step 5 — Prove it actually works

```bash
./scripts/smoke.sh https://razo-ai-api.onrender.com <API_KEY>
```

Eleven checks: health, the agent manifest, the catalog, a purchase that
clears, one escalated to the merchant, one refused by the hard cap, and the
audit chain verifying. If all eleven pass, the deployment is good.

---

## If something breaks

| Symptom | Cause | Fix |
|---|---|---|
| Blank page, CORS error in console | `CORS_ORIGINS` wrong or has a trailing slash | Exact origin, JSON array, no slash; redeploy API |
| Frontend calls `127.0.0.1` | `VITE_API_BASE_URL` set after the build | Set it, then **rebuild** the web service |
| `503 DB_UNAVAILABLE` | Atlas Network Access blocks Render | Allow `0.0.0.0/0` |
| First request hangs ~40s | Free-tier cold start | Expected — warm it up before demoing |
| `401` on writes | `VITE_API_KEY` ≠ API's `API_KEY` | Copy the generated value across |
| Chat replies feel templated | Both LLM keys missing or rate-limited | Expected fallback. Check `/health/ready` → `llm_breakers` |

### The escape hatch

If Atlas or Razorpay misbehaves an hour before you present, set
`OFFLINE_MODE=True` on the API service and redeploy. The whole system runs
self-contained — in-memory database, deterministic fake payments — and every
guardrail still fires. You lose real Razorpay order IDs; you keep the demo.
